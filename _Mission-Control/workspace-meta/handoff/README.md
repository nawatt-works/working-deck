# Handoff

พื้นที่ส่งต่องานระหว่าง producer ที่ทำหน้าที่ต่างกัน เช่น ตัวที่ออกแบบและวางแผน
ตัวที่ implement และตัวที่ตรวจสอบผล เอกสารในนี้ต่างจาก artifact ทั่วไปตรงที่มัน
ถูกเขียนเพื่อให้ **คนอื่นเอาไปทำต่อ** เจ้าของจึงเป็นตัวงาน ไม่ใช่ผู้เขียน

พื้นที่นี้เป็น **สายพาน ไม่ใช่คลังประวัติ** ห้ามใครอ้างอิงไฟล์ในนี้เป็นแหล่งความจริง
ถาวร ของที่ยังมีผลบังคับต้องถูกย้ายออกไปเมื่องานจบ

รูปแบบไฟล์และ schema อยู่ที่ `_Mission-Control/workspace-meta/contracts/handoff/`

## โครงสร้าง

```text
_Mission-Control/workspace-meta/handoff/
├── README.md
└── <work_id>/
    ├── 00-brief.md            # ผู้เปิดงาน (ไม่บังคับ)
    ├── 10-plan.md             # ผู้ออกแบบและวางแผน
    ├── 20-implementation.md   # ผู้ implement
    └── 30-audit.md            # ผู้ตรวจสอบ
```

หนึ่งโฟลเดอร์คือหนึ่งหน่วยงาน หนึ่งไฟล์คือหนึ่ง stage

## หน่วยงานเกิดขึ้นเมื่อไหร่

**เมื่อรู้ว่างานจะข้าม producer เท่านั้น** งานที่ทำจบในตัวเองไม่ต้องมีหน่วยงานและ
ไม่ต้องมีโฟลเดอร์ ให้เก็บ artifact ไว้ตาม convention ของ harness หรือ workflow
เจ้าของงานนั้น

จุดที่สร้างคือตอนจะเขียนไฟล์ stage แรกที่ตั้งใจให้ producer อื่นอ่าน ก่อนหน้านั้น
ยังไม่มีอะไรที่ต้องมีชื่อ ห้ามสร้างโฟลเดอร์หน่วยงานทิ้งไว้ล่วงหน้า

## `work_id`

**producer ตัวแรกที่สร้างไฟล์ stage แรกเป็นผู้กำหนด** ไม่ใช่ผู้ใช้

- รูปแบบคือ `YYYYMMDD-<kebab-slug>` เช่น `20260821-order-refund-flow`
- **slug ต้องมาจากคำที่ผู้ใช้ใช้เรียกงานนั้น** ไม่ใช่ศัพท์ที่ producer คิดขึ้นเอง
  เพราะผู้ใช้ต้องมองแล้วจำได้ว่าคืองานไหน
- วันที่คือ **วันที่เปิดหน่วยงาน ไม่ใช่วันที่แก้ล่าสุด** งานที่ลากหลายวันยังใช้เลข
  วันแรกตลอด
- **ต้องแจ้ง `work_id` กลับให้ผู้ใช้ทันทีที่สร้าง** ไม่งั้นผู้ใช้จะสั่งงาน producer
  ตัวถัดไปไม่ถูกเพราะไม่รู้ว่าหน่วยงานชื่ออะไร
- ก่อนสร้างหน่วยงานใหม่ **ต้องดูรายการใน `_Mission-Control/workspace-meta/handoff/` ก่อนเสมอ** ถ้ามี
  หน่วยงานที่ยังไม่ปิดและครอบคลุมเรื่องเดียวกัน ให้ต่อของเดิม ห้ามเปิดใหม่
- ถ้าชื่อชนกันจริง (วันเดียวกัน slug เดียวกัน) ให้ต่อท้ายด้วย `-2`

## Stage และสิทธิ์เขียน

ในพื้นที่นี้ **สิทธิ์เขียนกำหนดด้วย stage ไม่ใช่ตำแหน่ง artifact ของ producer**

- **หนึ่งไฟล์ stage มีผู้เขียนได้รายเดียว** คือ producer ที่รับผิดชอบ stage นั้น
  producer อื่นอ่านได้ทั้งหมด แต่ห้ามแก้ไฟล์ที่ไม่ใช่ stage ของตัวเอง
- ตอบกลับหรือโต้แย้งด้วยการเขียนไฟล์ stage ของตัวเอง ไม่ใช่แก้ไฟล์ของคนอื่น
- **รอบแก้ไขให้ append ลงไฟล์ stage เดิมของตัวเอง** เป็นหัวข้อ `## Round 2`
  ไม่ต้องสร้างไฟล์ใหม่ จำนวนไฟล์จะได้คงที่และไล่อ่านเป็นเส้นเวลาได้
- เลขนำหน้าเป็นตัวกำหนดลำดับ เว้นช่วงไว้ให้แทรก stage ใหม่ได้ · project ที่มี
  role ต่างจากนี้เพิ่ม stage ของตัวเองได้ ขอแค่คงรูปแบบ `<NN>-<stage>.md`
- ไฟล์แนบ เช่น diagram หรือ log ให้วางใน subdirectory ของหน่วยงานนั้น

## `status` คือสิ่งที่บอกว่าลงมือได้หรือยัง

- `draft` — ยังเขียนไม่เสร็จ producer อื่น **ห้ามลงมือทำตาม** ให้ถือว่ายังไม่มี
- `ready` — ส่งต่อแล้ว stage ถัดไปทำตามได้
- `superseded` — ถูกแทนที่แล้ว เก็บไว้เป็นบริบท ห้ามใช้เป็นฐานของงานใหม่

ถ้าไม่แน่ใจว่าไฟล์ที่เจอพร้อมหรือยัง ให้ถือตาม `status` เท่านั้น ห้ามเดาจากเนื้อหา

## เมื่องานจบ

ย้ายเฉพาะสิ่งที่ยังมีผลบังคับต่อ เช่น ข้อตัดสินใจหรือ spec ที่ยังใช้อยู่ ออกไปไว้ใน
ตำแหน่ง durable ที่ workflow เจ้าของงานกำหนด หรือใน repository ที่เกี่ยวข้อง แล้วลบ
โฟลเดอร์หน่วยงานนั้นได้
